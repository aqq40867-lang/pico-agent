## 0. 先建立心智模型

### 一句话（背下来）

pico 是一个**本地 coding agent harness**：把 LLM 包在一个受控的循环里，每一轮按预算拼 prompt → 让模型输出"一个工具调用或一个最终答案" → 经过安全护栏执行工具 → 把结果写回历史、记忆、checkpoint 和审计工件，直到停机条件满足。

### 一次 `pico "fix the bug"` 的完整链路

```
cli.main → build_agent（选 provider、加载 .env、构建 WorkspaceContext、新建/恢复 session）
  → Pico.__init__（注册工具 → 构建稳定 prefix → ContextManager → 评估 resume 状态）
  → Pico.ask → AgentLoop.run
      ├─ 记录 user 消息，TaskState.create，RunStore.start_run
      └─ while tool_steps < max_steps and attempts < max_attempts:
           1. 感知  _build_prompt_and_metadata：refresh_prefix → evaluate_resume_state → ContextManager.build
           2. 决策  model_client.complete(prompt) → Pico.parse → ("tool" | "retry" | "final")
           3. 行动  tool → ToolExecutor.execute（7 道检查）→ 写 history → trace → checkpoint
                    retry → 把错误提示写回 history，让模型自我纠正
                    final → _finish_success（沉淀长期记忆、checkpoint、report）
      └─ 工具预算耗尽 → 追加 "Do not call another tool" 提示再要一次 <final>（finalization）
```

- **什么是 agent？和直接调 API 聊天有什么区别？** 要点：聊天是一问一答；agent 是模型在循环中自主决定下一步动作（调用工具），根据环境反馈（工具结果）继续决策，直到完成任务。pico 的循环 = 感知（组 prompt）→ 决策（模型输出）→ 行动（执行工具）→ 记录（history/trace/memory）。

## Day 2：主循环与输出协议

**阅读顺序**
1. `pico/agent_loop.py`：`run()` 全文 → `_request_model()` → `_finish_success()` → `_persist_model_failure()`
2. `pico/runtime.py`：`parse()`、`parse_xml_tool()`、`retry_notice()`、`extract()`

4. `tests/test_agent_loop.py`

**动手**
- `uv run python study/fake_run_demo.py malformed`：看坏 JSON 如何变成 `retry`，attempts 加 1 但 tool_steps 不加
- `uv run python study/fake_run_demo.py budget`：看 `purpose: finalization` 那一轮
- 自己改 demo：让假模型输出一段同时含 `<tool>` 和 `<final>` 的文本，猜 parse 会选哪个，再验证

**面试题**
- **循环什么时候停？**
  - 模型返回 `<final>` → `completed / final_answer_returned`
  - 工具步数用完（默认 `max_steps=6`）→ 先追加 runtime notice 再要一次 `<final>`；拿不到就 `step_limit_reached`
  - 坏输出太多（`attempts >= max(3*max_steps, max_steps+4)`）→ `retry_limit_reached`
  - 模型请求异常 → `model_error`，status 是 `failed`，并且落 checkpoint 和 report
- **为什么分 `tool_steps` 和 `attempts`？** tool_steps 是"真正执行了几次工具"（行动预算），attempts 是"调了几次模型"（含格式错误重试）。分开才能区分"任务太难做不完"和"模型格式不听话"。
- **为什么 `status` 和 `stop_reason` 分开存？** 一个是"停下时是什么状态"（completed/stopped/failed），一个是"怎么停的"。同为 stopped，可能因为步数也可能因为重试。
- **模型输出格式错了怎么办？** 不抛异常，生成一段 `Runtime notice: ...` 写回 history（以 assistant 角色），下一轮模型能看到错误原因并自我纠正。
- **为什么用文本协议 `<tool>{json}</tool>`，而不用原生 function calling？**（高频）
  - 好处：provider 无关，Ollama 小模型、OpenAI Responses、Anthropic Messages 都只需要实现 `complete(prompt) -> text`；零依赖；完全可控、可测
  - 代价：解析脆弱，要靠 retry 机制兜底；不能用 provider 的原生并行工具调用；和 thinking 冲突（DeepSeek 路径显式 `thinking: disabled`，因为 thinking block 在文本协议下无法回放，还会吃掉输出预算）
  - 改进：接原生 tool use，同时实现 thinking block 的完整回放
- **为什么 write_file 推荐 XML 风格？** 多行代码塞进 JSON 字符串需要转义换行和引号，模型很容易写坏；XML 子标签 `<content>...</content>` 可以原样放代码。
- **输出里同时有 `<tool>` 和 `<final>` 怎么办？** 谁先出现取谁。
- **这是 ReAct 吗？** 是 ReAct 的变体：Action = 工具调用，Observation = 写回 history 的工具结果；Thought 没有显式要求输出。

## Day 3：工具系统与安全护栏（最常被深挖）

**阅读顺序**
1. `pico/tools.py`：`BASE_TOOL_SPECS` → `build_tool_registry()` → `validate_tool()` → `tool_run_shell()` → `tool_patch_file()`
2. `pico/tool_executor.py` 全文
3. `pico/runtime.py`：`path()`、`approve()`、`repeated_tool_call()`、`capture_workspace_snapshot()`、`diff_workspace_snapshots()`、`spawn_delegate()`
4. `pico/security.py`、`pico/tool_context.py`
5. `tests/test_safety_invariants.py`、`tests/test_security.py`、`tests/test_allowed_tools.py`

**动手**
- `uv run python study/fake_run_demo.py escape` 和 `repeat`，看 `tool_error_code` 和 `security_event_type`
- 思考题：假模型调用 `run_shell` 执行 `cat ../xxx`，会被拦吗？（答案：不会被路径沙箱拦，见下）

**面试题**
- **工具执行经过哪些检查？**（必背顺序）`ToolExecutor.execute`：
  1. 本次 run 的 `allowed_tools` 白名单
  2. 工具是否存在
  3. 参数校验（含路径沙箱、timeout 范围、patch 唯一性）
  4. 重复调用检测
  5. 风险工具审批（`run_shell / write_file / patch_file` 是 risky）
  6. 执行前后对工作区做 sha256 快照并 diff
  7. 状态分类：`ok / error / partial_success / rejected`，然后更新记忆、写失败经验
  - 所有失败都**返回字符串而不是抛异常**：模型能看到原因并换方案，循环不会因为工具失败崩掉
- **路径沙箱怎么做？** `Pico.path()`：先 `resolve()`（同时解析 `..` 和符号链接），再用 `os.path.commonpath` 判断是否仍在 repo root 下。追问"为什么不用 `startswith`？"：`/repo-evil` 也以 `/repo` 开头。
- **run_shell 安全吗？**（一定要主动说边界）
  - 已有：环境变量白名单（不继承 API key）、timeout 限制在 1~120 秒、cwd 固定、需要审批、输出截断 4000 字符
  - 没有：`shell=True` 的命令不受路径沙箱约束，能读写仓库外文件；timeout 只杀 shell 进程，子孙进程可能残留
  - 生产级做法：容器/沙箱（Docker、bubblewrap、seccomp）、命令白名单、禁网、进程组 kill
- **patch_file 为什么要求 old_text 恰好出现一次？** 修改行为确定、失败可解释（"找到 0 次/2 次"）；行号补丁会因文件变化而漂移。和 Claude Code 的 Edit 工具是同一思路。
- **重复调用怎么检测？局限？** 最近两次工具调用与本次 name+args 完全相同 → 第三次拒绝。局限：A-B-A-B 震荡、参数微小变化都抓不到。注意被拒绝的调用也消耗 tool_steps（防止死循环）。
- **审批机制？** `--approval ask/auto/never` + `read_only`；ask 模式下 stdin EOF 视为拒绝（fail-closed）。审批拒绝不会终止 run，而是把 `approval denied` 回给模型让它换路。
- **partial_success 是什么？为什么需要？** shell 退出码非 0 但工作区已经变了，或工具中途抛异常但文件已被改 → 标 partial_success 并写一条 process note："先看 diff 再重试"，防止模型盲目重试叠加破坏。靠执行前后的 sha256 快照 diff 实现。
- **delegate 子 agent 怎么设计的？**
  - 深度限制 `max_depth=1`：深度耗尽时连 delegate 工具都不暴露给模型
  - 子 agent 是 `read_only=True`、`approval=never`、`max_steps=3`
  - 只把结论文本返回给父 agent（上下文隔离，不污染父上下文）
  - 为什么只读？委派的是"调查"而不是"权限"，避免权限放大和并发写冲突
- **trace 里的密钥怎么脱敏？** `redact_artifact` 递归处理：key 名像密钥（`*_API_KEY / TOKEN / SECRET / PASSWORD`）→ 整个值替换；字符串里出现密钥值 → 替换成 `<redacted>`，并且按长度从长到短替换，避免短值把长值切碎。
- **allowed_tools 有什么用？** 按任务给最小权限（benchmark 里每题只开放需要的工具），也是最小权限原则的体现。

## Day 4：上下文工程与 Prompt 缓存

**阅读顺序**
1. `pico/context_manager.py`：`build()` → `_render_sections()` → `_render_history_section()` → `_compressed_history_entries()` → `_render_relevant_memory()`
2. `pico/prompt_prefix.py` 全文
3. `pico/workspace.py`：`WorkspaceContext.build()`、`text()`、`fingerprint()`
4. `pico/runtime.py`：`refresh_prefix()`、`_build_prompt_and_metadata()`
5. `tests/test_context_manager.py`、`tests/test_prompt_prefix.py`

**动手**
- 在 demo 里 `print(model.prompts[0])`，看完整 prompt 长什么样
- 把 `DEFAULT_TOTAL_BUDGET` 临时改成 3000，跑 demo，看 trace 里的 `budget_reductions` 和 `checkpoint_created(trigger=context_reduction)`

**面试题**
- **prompt 由哪几段组成？为什么这个顺序？** `prefix`（规则 + 工具说明 + 工作区快照 + checkpoint）→ `memory` → `relevant_memory` → `history` → `current_request`。稳定内容放前面，让前缀缓存能命中；最新请求放最后，离生成最近，模型最重视。
- **超预算怎么压缩？**（高频）
  - 总预算 12000 字符；每段有 budget 和 floor（floor = budget // 4）
  - 按 `relevant_memory → history → memory → prefix` 的顺序，每次只压一段，压掉溢出量，但不低于 floor
  - **当前请求永不裁剪**
  - 为什么这个顺序：召回笔记最"可选"；历史可以靠摘要替代；工作记忆和规则最不能丢
- **历史怎么压？** 最近 6 条保留（每条最多 900 字符）；更早的：重复 `read_file` 折叠、有新鲜文件摘要就用摘要替代原文、`run_shell` 只留前 3 行、其他旧工具调用只保留调用那一行、旧对话截到 60 字符；从新往旧填进预算。
- **为什么按字符而不是 token？** 零依赖、跨 provider 一致、确定可测；缺点是中文和代码的 token 比例不一样，不精确。改进：tiktoken 或 provider 的 count_tokens 接口。
- **Prompt 缓存怎么做的？**
  - prefix 单独构建并算 sha256 作为 `prompt_cache_key`；只有工作区指纹或工具签名变化时才重建
  - OpenAI-compatible 后端传 `prompt_cache_key`，从 usage 里取 `cached_tokens` 记录 `cache_hit`，写进 trace/report
  - **追问陷阱**：工作区快照里有 `git status --short`，写一次文件 status 就变了 → 指纹变 → prefix 重建 → 缓存失效。改进：把易变的 git status 移出 prefix 放到动态段。Anthropic 路径也没接 `cache_control`。
- **每轮重新拼整份 prompt（单条 user 消息）和多轮 messages 数组相比？** 好处：完全可控、可压缩、可审计（metadata 记录每段原始/渲染长度）；代价：动态部分每轮重新计费，用不上 provider 的多轮对话结构。
- **和 LLM 摘要式压缩（compaction）比？** pico 是规则式、确定性压缩：不额外调用模型、可测；缺点是不够"聪明"，可能丢掉重要细节。
- **工作区快照为什么只读 4 个文件，每个 1200 字符？** `AGENTS.md / README.md / pyproject.toml / package.json` 是"导航包"，其余按需用工具读（just-in-time），避免一开始就把仓库塞满上下文。

**阅读顺序**
1. `pico/features/memory.py`：`default_memory_state()` → `normalize_memory_state()` → `set_file_summary() / file_freshness()` → `retrieval_candidates()` → `render_memory_text()` → `DurableMemoryStore.promote()` 和 `_subject_key()`

3. `tests/test_memory.py`

**动手**
- 改 demo：用户请求里写 "remember ..."，假模型 final 里写一行 `Decision: use uv for dependency management`，运行后检查临时仓库里的 `.pico/memory/MEMORY.md` 和 `topics/key-decisions.md`
- 真实运行时在 REPL 里试 `/memory`

**面试题**
- **记忆分几层？**
  1. `history`：完整事件流（存在 session json，供压缩后放进 transcript）
  2. `working`：当前任务摘要 + 最近 8 个文件
  3. `file_summaries`：读文件时提取前三行摘要，并存文件 sha256 作为新鲜度
  4. `episodic_notes`：最多 12 条笔记，包括工具失败时自动写的 process note
  5. `durable`：跨会话长期记忆，`.pico/memory/MEMORY.md` + `topics/*.md`，四个主题（项目约定、关键决策、依赖事实、用户偏好）
- **怎么防止记忆过期？** 文件摘要带 sha256；每轮 `evaluate_resume_state` 都会 `invalidate_stale_file_summaries`；写文件/patch 后立即删掉对应摘要；渲染时再比一次新鲜度。
- **召回怎么做？为什么不用向量库？**
  - 排序键：(tag 精确命中, 关键词重叠数, 时间, note 序号)，取 top 3
  - 理由：数据量很小（≤12 条 + 少量长期记忆），确定性、可解释、可测、零依赖
  - **局限（主动说）**：`_tokenize` 只匹配 `[A-Za-z0-9_]`，中文内容完全切不出 token，中文查询召回不到；也没有同义词/语义匹配。改进：中文分词或 embedding 混合检索。
- **长期记忆的写入门槛？**（高频，体现安全意识）三道闸：
  1. 用户有显式意图（remember / save / 记住 / 保存 …）
  2. 模型 final 里出现固定前缀行（`Decision:`、`Project convention:`、`Dependency:`、`Preference:` 或中文版）
  3. 拒绝规则：像密钥的、像临时任务状态的（"next step / 当前目标"）、像噪声输出的（含 stdout/traceback 或超过 220 字符）
  - 冲突处理：按"主语"（`X is / uses / should …`）识别同一事实，新的替换旧的（supersede）并记录
  - 为什么这么保守：防记忆污染（被 prompt injection 写进持久记忆）、防泄密、防把临时状态当长期事实
- **process note 是什么？** 工具出错/被拒/部分成功时自动写一条经验（如 "patch_file error on x; check the failure before retry"），之后能被召回。类似 Reflexion 的失败反思，但是规则化的。

**面试题**
- **checkpoint 存什么？什么时候存？**
  - 内容：当前目标、blocker、next_step、关键文件及其 sha256、运行身份（model、审批策略、工具签名、工作区指纹等）、`parent_checkpoint_id`（形成链）
  - 时机：每次工具执行后、正常结束、上下文被压缩、新鲜度不一致、工作区不一致、模型报错、步数耗尽
- **恢复时如何判断旧状态是否可信？**（高频）五种状态：
  - `no-checkpoint`
  - `full-valid`：可直接接着做
  - `partial-stale`：关键文件 hash 变了 → 在 prompt 里列出 stale paths，让模型重新读（re-anchor）
  - `workspace-mismatch`：运行身份字段变了（换了模型、换了审批策略、工具集变了……）
  - `schema-mismatch`：checkpoint 格式版本不对
  - 核心思想：**不盲信旧状态**。"false accept"（旧状态已过期却仍被当真）就是专门测这个的指标
- **三类运行工件有什么区别？**
  - `task_state.json`：当前状态快照，原子写，运行中也能观察
  - `trace.jsonl`：追加写的事件流（prompt_built / model_requested / model_parsed / tool_executed / checkpoint_created / run_finished，带耗时），回答"过程中发生了什么"
  - `report.json`：最终摘要 + prompt metadata + 记忆变更，回答"结果是什么"
  - session json 存"可恢复的会话状态"，和 run 工件分开：恢复现场 vs 审计证据
- **为什么要原子写？** 先写临时文件再 `replace`，中途崩溃也不会留下半截 JSON。追问：`SessionStore.save` 是直接 `write_text`，并不是原子写，这是一个不一致、可以改进的地方。
- **provider 抽象怎么做的？**
  - 鸭子类型：`complete(prompt, max_new_tokens, **kwargs)` + `supports_prompt_cache` + `last_completion_metadata`
  - 3 种 HTTP 协议客户端（Ollama、OpenAI Responses、Anthropic Messages），4 个 provider 配置（DeepSeek 复用 Anthropic 兼容客户端）
  - 纯 `urllib`，零第三方依赖；同时兼容 JSON 和 SSE 响应
  - 5xx 和网络错误重试 3 次、线性退避；**4xx 不重试，包括 429 限流**（改进：指数退避 + jitter + 读 Retry-After）
- **FakeModelClient 有什么意义？** 按剧本返回输出，让 harness 测试摆脱网络和模型随机性，可重复。
- **配置优先级？** CLI 参数 > `.env` 里的 `PICO_*` > 旧环境变量 > 默认值。API key 只从环境变量读，不接受命令行参数（防止进 shell history）。

**每个数字怎么来的、能证明什么、不能证明什么**

| 简历数字 | 怎么测的 | 能证明 | 不能证明 |
|---|---|---|---|
| 回归 12 题 100% 通过 | 12 个固定任务（文档 2、文本编辑 2、工具边界 3、恢复 3、长期记忆 2），脚本化模型输出 + 每题 verifier 检查最终工作区和工件 | runtime 合同稳定，改代码不会改坏 | 模型/agent 的真实解题能力 |
| prompt 平均压缩 16%，最高 33%，当前请求 100% 保留 | 12 组压力配置（3 档历史 × 2 档笔记 × 2 档请求），对比开/关上下文治理的字符数 | 压缩机制有效且不伤当前请求 | 压缩后模型效果没有下降 |
| 重复读文件 60 → 0 | 12 个任务 × 5 次；脚本模型规则："事实在 Memory/Relevant memory 段里就直接回答，否则再读一次文件" | harness 确实把事实放进了 prompt | 真实 LLM 一定会利用这些记忆 |
| 恢复 10 场景，漂移识别 100%，false accept 0 | 10 个任务 × 3 次；脚本模型检查 prompt 里是否包含必需的恢复片段 | checkpoint/新鲜度判定逻辑正确 | 真实模型恢复后能把任务做完 |

**被质疑"用假模型 100% 不是理所当然吗？"时这样答**：
> 这组实验的定位是 harness 的回归和消融，用脚本化模型隔离模型随机性，验证的是运行时机制本身——比如工具边界有没有守住、记忆有没有进 prompt、过期状态会不会被误信。verifier 检查的是最终工作区和运行工件，而不是模型自己说"完成了"。真实模型能力需要另外做端到端评测，比如 SWE-bench 类任务配合 pass@k 多次采样，这是我下一步要补的。

**简历措辞建议**：DATA_PROVENANCE 里已经提示"2 类模型后端"是早期口径，建议改成"支持 4 个 provider 配置（3 种 API 协议）"，避免被当场对不上。

## 项目的短板与改进方向（主动说出来是加分项）

1. **run_shell 没有真正的沙箱**：不受路径限制、timeout 只杀 shell 进程 → 容器隔离、命令白名单、禁网、进程组 kill
2. **文本工具协议** → 原生 tool calling、并行工具调用、thinking 回放
3. **按字符计预算** → 按 token 计
4. **缓存命中受 git status 影响**；Anthropic 路径没接 `cache_control`
5. **召回不支持中文**（`_tokenize` 只认 ASCII）、没有语义召回
6. **每个风险工具执行前后都对全仓做 sha256 快照** → 大仓库开销 O(文件数)，可以改成 `git diff` 或 mtime 增量
7. **重复调用检测只抓连续完全相同的调用**
8. **session 保存不是原子写**，而且每条记录都全量重写 session json
9. **429 不重试**、线性退避而非指数退避
10. 定义了 `tool_timeout / approval_denied / delegate_failed` 等 stop_reason 但没有使用
11. 单线程串行、没有流式输出
12. **评测只有脚本化模型**，缺少真实模型的端到端 benchmark
